# Quant Workbench Demo v1 开发计划与 Agent 协作规则

- 状态：执行计划草案，日历日期待启动日确定
- 关联：[PRD](PRD-demo-v1.md)、[技术方案与选型](TECHNICAL-DESIGN.md)

## 1. 计划原则

- 总体按阶段和验收门推进，不让多人同时改同一文件。
- 下表的 D1、D2 表示项目启动后的工作日，不是日历日期；启动日确认后再生成日期版进度表。
- UI 原型是正式任务，先由原型 agent 交付独立 HTML；原型评审后，前端实现再开始。
- 先冻结接口和文件所有权，再分支并行开发。
- 里程碑日期是目标，不得越过质量门强行合并。
- P0 闭环优先；延期先砍 P1 和视觉细节，不砍交易正确性、数据质量和测试。

## 2. Agent 编制（建议 5 个角色）

总指挥官可以用角色名识别会话，用户之后可通过 intercom 指定实际 agent。

| 代号/名字 | 角色 | 主要责任 | 不负责 |
|---|---|---|---|
| **舵手** | 主指挥官 | 维护需求基线、拆解和分派任务、冻结接口、协调冲突、决定合并、向用户汇报 | 不独自吞并所有模块开发 |
| **副舵手** | 副指挥官/集成负责人 | 跟踪依赖和进度、主持接口检查、维护集成环境、检查 agent 文件所有权和阻塞项 | 不自行变更产品范围或合并未过审代码 |
| **算盘** | 数据与量化开发 | 数据接入/校验、指标、筛选、回测和对应测试 | 不改 UI、PRD 基线和公共 API schema |
| **舱面** | UI/原型开发 | HTML 原型、桌面前端、交互状态和前端测试 | 不定义金融口径、不私自改后端契约 |
| **审计员** | Reviewer/质量负责人 | 独立检查需求覆盖、金融正确性、测试、许可证、可维护性和安全 | 不在 review 分支直接修开发者代码；发现问题退回责任 agent |

若实际只有 4 个 agent，合并副舵手与审计员职责需用户确认；不能由主指挥官同时开发又自审关键交易逻辑。

## 3. 汇报与决策权限

### L0：Agent 自主决策

在已批准需求、接口和文件范围内，责任 agent 可自行处理：变量/函数命名、局部实现、测试写法、无行为变化的整理、普通依赖内部实现细节。完成后在任务记录中说明，不必打断用户。

### L1：主指挥官决策

舵手可决定：任务顺序和拆分、已冻结接口内的实现选择、非破坏性依赖替换建议、局部技术债接受期限、P1 降级/延期建议、代码风格和分支安排。涉及其他模块时先和副舵手及所有者同步。

### L2：副指挥官协调后由主指挥官批准

涉及模块边界/API schema、共享数据模型、公共任务状态、跨模块依赖、文件所有权冲突、可能阻塞其他 agent 的变更。副舵手先组织受影响 agent 给出影响和方案，舵手做项目内决定；若触及产品行为则升级用户。

### L3：必须向项目创建者（用户）汇报并等待确认

- 产品范围、P0/P1/P2、验收标准或用户工作流改变；
- 指标公式、基准、样本过滤、交易规则或数据口径改变；
- 可能产生错误交易结论、数据丢失、凭证暴露或安全边界变化；
- 采用 AGPL/商业限制不明代码、增加有重大维护成本的依赖；
- 预算、AutoDL 资源或服务暴露方式的明显改变；
- 里程碑预计延迟超过 2 个工作日或必须砍 P0；
- 用户数据删除、覆盖、迁移且无法无损回滚；
- 任何超出已批准范围的实盘/下单能力。

紧急安全问题可先关闭受影响功能/凭证并立即报告；不得自行做不可逆修复。

## 4. 交流与任务规则

### 4.1 任务卡格式

每项任务记录在 `tasks/`，至少写：

- 任务 ID、标题、状态、优先级；
- 对应 PRD 需求编号；
- 负责人和 reviewer；
- 输入依赖、交付接口；
- 文件所有权范围；
- 验收步骤和测试命令；
- 分支名、提交链接/哈希；
- 阻塞项和风险。

状态仅使用：`待办`、`进行中`、`待评审`、`阻塞`、`完成`。

### 4.2 Intercom 约定

- 任务开始：负责人发送任务 ID、目标、预计文件范围和依赖。
- 接口准备冻结：副舵手发 schema/示例，请相关 agent 回复确认或指出冲突。
- 发现阻塞：立即报告阻塞原因、影响任务、需要谁决定；不要静默等待。
- 任务完成：发送分支、提交、测试结果、未解决问题和 reviewer 请求。
- 决策升级：按 L0-L3 标级；L3 明确标注“等待用户确认”，未确认不继续不可逆或超范围工作。

避免频繁广播。一个接口或变更只指定一名协调者，其他人在线程回复。

### 4.3 分支与文件所有权

每个实现任务独立分支，建议格式：`feat/<task-id>-<short-name>`；修复为 `fix/<task-id>-<short-name>`。不在同一工作树并行改相同文件。共享 schema 由舵手指定单一负责人维护；接口冻结后，改动先走 L2/L3 决策流程。

建议初始所有权：

| 路径 | 主要所有者 |
|---|---|
| `docs/PRD-demo-v1.md` | 舵手；用户批准产品改动 |
| `docs/TECHNICAL-DESIGN.md` | 副舵手；舵手批准接口决策 |
| `docs/DEVELOPMENT-PLAN.md`、`tasks/` | 副舵手 |
| `prototype/` | 舱面（原型阶段） |
| `src/backend/data/`、`src/backend/research/`、`src/backend/backtest/` | 算盘 |
| `src/backend/api/`、`src/backend/mcp/`、共享 schema | 副舵手指定单一 owner |
| `src/desktop/` | 舱面 |
| CI、集成测试和合并配置 | 副舵手 |

目录结构在技术验证完成后再建立；该表是预期所有权，不要求现在创建空目录。

## 5. 评审与合并闸门

任何分支合并前必须满足：

1. 对应 PRD 验收项完成，或明确记录未完成范围；
2. 单元/集成测试通过，新增金融逻辑包含边界测试；
3. Reviewer 无未解决的阻塞级问题；
4. 复用项已登记到 `research/REUSE-REGISTER.md`，含层级、来源 commit、许可证和改动范围；L3 改造有文件头出处；
5. 无密钥、个人数据或大体积生成数据进入提交；
6. API/schema 变更已由受影响 owner 确认；
7. 任务记录包含运行命令和结果；
8. 舵手最终批准并执行合并。

审查严重度：

- **阻塞**：金融结果错误、数据破坏/泄漏、安全漏洞、需求不符、关键测试失败；必须修复。
- **重要**：明显性能/维护问题或关键边界缺测试；修复或经舵手记录例外后合并。
- **一般**：可读性、非关键改进；可开后续任务，不阻塞当前合并。

Reviewer 不以个人偏好阻止等价实现；意见必须关联需求、缺陷、风险或可验证收益。

## 6. 进度安排（启动后工作日）

### 阶段 0：范围与原型，D1–D4

| 时间 | 负责人 | 任务 | 验收/依赖 |
|---|---|---|---|
| D1 上午 | 舵手 + 用户 | 评审 PRD 的 P0、关键指标和交易范围 | 用户确认产品决定；未决项列清单 |
| D1 下午 | 副舵手 | 建任务卡、需求编号草案、仓库/分支和接口评审流程 | 任务模板和责任人可用 |
| D1–D2 | 算盘 + 副舵手 | 按“先找现成”原则调研功能级复用候选，登记 REUSE-REGISTER | 每个能力记录层级/许可证/替代方案或自研理由 |
| D2–D3 | 算盘 | 验证 GitHub 数据包候选的股票覆盖、历史长度、复权、ST/新股状态、交易日历、更新和许可 | 对 PRD 市场范围逐项给出通过/缺失证据 |
| D1–D2 | 舱面 | 读 PRD，列页面/状态/交互清单；不先自行增加功能 | 交互清单获得舵手确认 |
| D2–D3 | 舱面 | 制作独立 HTML 可点击原型：复盘→个股→筛选→回测→任务/Agent | 全流程可演示；内置 Agent 面板与 MCP 均有入口；假数据明确标注 |
| D3 | 审计员 | 原型与 PRD 一致性评审、移动/窄窗口和空/错状态检查 | 阻塞问题清单 |
| D4 | 用户 + 舵手 | 原型评审、确定 P0 和范围冻结 | 原型通过或明确返工项；PRD v1 基线标记 |

### 阶段 1：技术验证与契约冻结，D5–D7

| 时间 | 负责人 | 任务 | 验收/依赖 |
|---|---|---|---|
| D5 | 副舵手 | 确定运行边界、API 草案、任务模型和数据目录约定 | 受影响 agent 确认 schema |
| D5–D6 | 算盘 | AutoDL 上最小数据拉取、DuckDB/Parquet 查询和质量检查 spike | 可重复运行；字段与复权风险记录 |
| D5–D6 | 舱面 | Tauri/React 最小客户端连接健康 API 和 SSE | 显示连通、断开及重连状态 |
| D6 | 算盘 + 副舵手 | 验证任务断线后查询恢复、单写者数据更新和备份恢复 | 过程记录与失败处理明确 |
| D7 | 审计员 | 审查技术验证、依赖许可证、接口安全和范围 | 无阻塞风险；未决项升级用户 |
| D7 | 舵手 | 技术决策记录定稿并冻结接口 | 决策记录有理由、替代项和复查条件 |

### 阶段 2：后端闭环，D8–D14

| 时间 | 负责人 | 任务 | 验收/依赖 |
|---|---|---|---|
| D8–D10 | 算盘 | 数据更新、日历/状态、质量告警和基础查询 | 固定样例测试通过；失败可见 |
| D8–D10 | 舱面 | 搭建工作台壳、导航、工作区、右栏和底部任务栏 | 使用原型布局；接 mock API，不造新需求 |
| D9–D11 | 副舵手 | API schema、任务状态 API、日志/产物引用和 SSE | 契约测试通过，字段冻结 |
| D10–D12 | 算盘 | 复盘指标、个股查询和筛选 P0 | 指标字典对应测试通过，结果含样本量 |
| D11–D13 | 算盘 | 日频回测最小实现与交易规则边界测试 | 黄金样本通过，基准/超额和成交记录可复现 |
| D12–D14 | 舱面 | 复盘、个股、筛选和任务页面接真实 API | 空、加载、错误、过期状态完整 |
| D14 | 审计员 | 后端闭环 review | 金融正确性、测试、许可证和安全无阻塞项 |

### 阶段 3：Agent、集成与验收，D15–D20

| 时间 | 负责人 | 任务 | 验收/依赖 |
|---|---|---|---|
| D15–D16 | 副舵手 | MCP 工具实现/适配业务服务、错误与版本字段 | MCP 契约测试通过；无重复业务逻辑 |
| D15–D17 | 舱面 | Agent 面板、工具调用卡片、回测配置/结果页 | 工具参数和任务结果可追踪 |
| D16–D17 | 算盘 | 端到端数据与回测样例、异常数据防护 | 用固定区间完整运行并留结果 |
| D18 | 全体；舵手协调 | 集成测试：复盘→个股→筛选→回测→Agent 查询任务 | 流程无人工改库/命令绕行 |
| D19 | 审计员 | 全量 review 和风险复核 | 阻塞级问题清零；其他问题有任务记录 |
| D20 | 用户 + 舵手 | Demo v1 验收和范围回顾 | 验收场景通过，遗留项转 v1.1，不暗中扩 scope |

以上为目标节奏，不是无条件承诺。若阶段门不通过，舵手先报告原因和方案；涉及 P0、超过 2 个工作日延期或预算/范围变化时必须用户批准。

## 7. 开发进度表字段

实际任务执行时在 `tasks/` 建任务卡，开发进度总表至少包含：

`ID | PRD需求 | 优先级 | 任务 | 负责人 | Reviewer | 依赖 | 分支 | 计划时间 | 当前状态 | 验收/测试 | 阻塞/决策`

任务按接口与文件边界切分。一个任务尽量只由一个 agent 实现，其他 agent 提供 review 或输入。

## 8. 变更管理

- 未冻结：用户和舵手可修改 PRD；所有受影响任务同步更新。
- 已冻结：产品行为、指标口径和交易规则变更必须用户批准，并记录版本和迁移影响。
- 技术实现调整但不改变外部行为：舵手可批准，技术设计记录原因。
- 公共 API/MCP schema 调整：副舵手做影响分析，舵手批准；涉及产品行为时升级用户。
- 紧急缺陷：先停止错误结果继续传播，再通知用户/舵手；修复仍需 review 和回归测试。

## 9. 用户汇报节奏

- 阶段开始：舵手报告目标、负责人、依赖和预计阶段门。
- 每个工作日结束：副舵手汇总完成、下一步、阻塞；只汇报状态变化，不刷无信息进度。
- 阶段门：提交验收证据和未决风险，等待必要批准后继续。
- L3 决策：明确列出选项、影响、推荐项和最晚决策点；未获回复时保持安全默认，不擅自扩大权限或改产品口径。

## 10. 当前启动前事项

1. 用户已确认市场范围、沪深 300 默认基准、GitHub 数据包优先策略及内置 Agent + MCP；
2. 确认数据历史长度、指标口径、桌面端最小分辨率和 AutoDL 服务访问方式；
3. 用户通过 intercom 指定各角色对应的实际 agent 会话；
4. 由用户提供 Git 提交身份，完成暂存文档的基线提交；
5. 建立真实开发分支后再派发代码任务；
6. 原型任务先执行，不与前端真实实现并行改同一目录。
